# Reporter de mercado y predicciones a 24 h — Plan de implementación

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Construir `reporter\`: cada 4 h baja velas de 4 pares de Binance, genera informe + predicción base, la guarda, la evalúa a 24 h y la envía a Telegram.

**Architecture:** Siete módulos pequeños (`candles`, `indicators`, `report`, `baseline`, `journal`, `notify`, `run`), funciones puras donde sea posible, SQLite para el journal. El paso de Claude se conectará después sustituyendo solo `baseline.py`.

**Tech Stack:** Python del `.venv` del proyecto, `requests`, `pandas`, `numpy`, `sqlite3`. Pruebas sin red en `reporter\test_reporter.py`, mismo estilo que `monitor\test_monitor.py` (funciones `test_*` + bloque `__main__`, sin pytest).

**Spec:** `docs\superpowers\specs\2026-11-09-reporter-design.md`

## Global Constraints

- Pares: `BTCUSDT`, `ETHUSDT`, `SOLUSDT`, `ADAUSDT`. Ventanas: 4h × 60 días, 1h × 15 días, 15m × 24 h.
- Solo analiza y avisa: sin claves de Binance, sin operar. Sin asesoría financiera (el informe lo indica).
- Binance sin key; si `api.binance.com` responde 451 usar `data-api.binance.vision`.
- Token de Telegram solo de `TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHAT_ID`; nunca se imprime ni se escribe en archivos.
- Rutas relativas a la carpeta del proyecto; salidas en `reporter\out\`; `monitor.db` solo lectura.
- Texto de noticias = no confiable: solo se muestra.
- Un solo proceso a la vez (archivo de bloqueo). Se cuentan corridas, no predicciones, como tamaño de muestra.
- No hay repositorio git en la carpeta: los pasos "Commit" se omiten salvo que el usuario haga `git init`.

## Review Focus

- Moneda que falla en la descarga: las otras siguen y la fallida no genera predicción (Task 5).
- Velas con huecos o fuera de orden: se rechazan, no se calculan indicadores con ellas (Task 1).
- `monitor.db` ausente o bloqueada por el monitor: el informe sigue y lo indica (Task 3).
- Segunda copia lanzada a la vez: sale con aviso, no corrompe `journal.db` (Task 5).
- Predicción sin precio a +24 h todavía disponible (red caída): queda pendiente, no se evalúa ni se borra (Task 4).

### Task 4: Predictor base y journal

**Files:**
- Create: `reporter/baseline.py`, `reporter/journal.py`; Test: `reporter/test_reporter.py`

**Interfaces:**
- Consumes: `summary` de `coin_block`.
- Produces (baseline): `predict(summary: dict) -> dict` con `prob_up: float` (0.05–0.95; punto de partida 0.5, +0.10 si `trend_4h=="up"`, −0.10 si `"down"`, −0.05 si `rsi_4h>70`, +0.05 si `<30`), `invalidation: float`, `note: str`; `reference_50() -> float` (0.5); `reference_momentum(chg_24h: float) -> float` (0.6 si >0, 0.4 si <0, 0.5 si 0).
- Produces (journal): `class Journal(path: str)` con `start_run(ts: str) -> int`, `end_run(run_id: int, ok: bool, note: str)`, `save_prediction(run_id: int, symbol: str, ts: str, price: float, prob_up: float, method: str)`, `pending(now: str) -> list[dict]` (predicciones con ≥24 h sin evaluar), `resolve(pred_id: int, price_24h: float)` (guarda `outcome` 1 si subió, y el Brier `(p-outcome)^2`), `stats() -> dict` (por moneda y global: `n_runs, n_resolved, accuracy, brier`, y lo mismo para las dos referencias).
- La referencia se guarda junto a cada predicción (columnas `ref50`, `ref_mom`) para comparar con los mismos datos.

- [ ] **Step 1: Pruebas** `test_baseline_bounds` (prob siempre dentro de 0.05–0.95 con RSI/tendencia extremos), `test_journal_resolve_brier` (prob 0.7, subió → Brier 0.09), `test_journal_pending_only_after_24h`, `test_resolve_missing_price_keeps_pending` (no se llama `resolve` → sigue pendiente), `test_stats_counts_runs_not_predictions`.
- [ ] **Step 2:** Ejecutar. Esperado: FALLA.
- [ ] **Step 3:** Implementar en SQLite (`journal.db`: tablas `runs`, `predictions`). Fechas en UTC ISO `%Y-%m-%dT%H:%M:%SZ`, como `monitor\store.py`.
- [ ] **Step 4:** Ejecutar. Esperado: PASAN.

### Task 5: Telegram y orquestador

**Files:**
- Create: `reporter/notify.py`, `reporter/run.py`, `reporter/README.md`; Test: `reporter/test_reporter.py`

**Interfaces:**
- Consumes: todo lo anterior.
- Produces: `notify.send(text: str) -> bool` (lee token y chat id del entorno; sin variables escribe en `out/` y devuelve False; recorta a 4000 caracteres; nunca imprime el token); `run.run_once(out_dir: str, fetcher=candles.fetch_all) -> dict` (inyectar `fetcher` permite probar sin red; devuelve `{"ok": [...], "failed": [...]}`); CLI `run.py --once | --stats` y bucle cada 4 h por defecto.
- Flujo de `run_once`: tomar bloqueo → `start_run` → resolver pendientes con el precio de la vela 15m más cercana a +24 h (si no hay precio, quedan pendientes) → por moneda: fetch, `coin_block`; si falla, marcar "sin datos" y seguir → `baseline.predict` y `save_prediction` solo de las monedas OK → escribir `report.md`, `predictions.jsonl`, `stats.md` → `notify.send` → `end_run` → liberar bloqueo.
